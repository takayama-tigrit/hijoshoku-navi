# 記事制作・トンマナの編集契約

## 主参照と、このサイトの主題

唯一の主参照は[北欧、暮らしの道具店](https://hokuohkurashi.com/)。具体的な読み物の参照は[日常着ニットの開発・着回し記事](https://hokuohkurashi.com/note/1000000901)。画面の測定値・再現範囲・例外は [design-reference.md](design-reference.md) に従う。他媒体の型を混ぜず、写真、短い段落、控えめな見出し、具体物から使う場面へ進む流れを移す。固有の文章・写真・ロゴ・人物は転用しない。

非常食ナビの主題は「いつもの食事のそばに、無理なく備えを置く」。水、ごはん、パン、おかず、袋の表示など、読者が確かめられる物から始める。災害への恐怖や抽象的な安心で購入を促さない。トップの主役は家庭備蓄のガイドとし、用途比較とアルファ米の記事を続ける。

参照記事にはオリジナル商品の開発と販売がある。「独自商品を持たないメディア」の事例として扱わない。編集と商品紹介がつながる構成を参考にするのであって、その見た目が事業成功の原因だとは断定しない。別の題材へ移せるのは編集とUIの型であり、集客・売上・収益を保証するものではない。

## 共通の編集手順 — 題材を替えても残すもの

1. **原文と根拠を固定する。** 文書を分類し、数値・日付・商品名・URL・結論・条件・警告・未確認事項を命題単位で保存する。安全情報や手順がある記事は局所改稿にとどめ、章順、手順、重大リスクの初出位置を動かさない。
2. **具体物と使い道をタイトルにする。** ごはんを選ぶ、水を数えるなど、その記事で確かめる対象を書く。問いを置くなら本文で答える。「いざという日に何食必要？」は問いの例であり、食数を袋数や栄養の充足と同一視しない。全記事を同じ疑問形や「○○から始める」で揃えない。
3. **写真と入り口を合わせる。** `coverPhoto`を設定し、記事冒頭に一度だけ表示する。同じ写真を本文先頭に重ねない。一般写真は題材の導入として使い、タイトル・alt・配置で商品現物や実食の証拠に見せない。写真下の免責や許諾detailsは付けない。参照先の人物署名をまねて、架空の編集者を置かない。
4. **結論を具体物から述べる。** 商品や家の在庫、その使用条件から始める。前置きや季節の情景を足して結論を遅らせない。参照記事の着用場面に相当する役割を、備蓄では調理・食事・保存の場面で担う。ただし実体験や感想は、記録がなければ書かない。
5. **段落を短く、均一にはしない。** 一段落で一つの話をする。写真、短い説明、仕様や図、選ぶためのリンクを必要な順に置き、毎節で同じ構造を反復しない。見出しを言い換えるだけの一文、説明予定の実況、過剰な美文は足さない。
6. **穏やかな語り口と、明確な警告を両立する。** 通常の説明は控えめにする一方、危険や例外を曖昧にしない。「安心」「大丈夫」「これだけで十分」を根拠なく使わない。安全上の条件は関連箇所で一度わかりやすく伝え、編集監査の定型文を繰り返さない。
7. **読者が確かめる一歩へつなぐ。** 表示を照合する、在庫を数える、メモを保存するなど、本文に対応する行動で終える。買わない選択も残し、全記事へ同じ購入CTAを付けない。
8. **表現と事実を別々に点検する。** まず命題・順序・留保を原文と照合し、その後に語彙と文の調子を整え、再照合する。体験、感情、人物の発言、比較の優劣、因果、読者反応が根拠なく増えていたら削除する。直せなければ公開を止める。

### トップと記事で共有する項目

- `seriesTitle`：記事の題材が分かる短い連載ラベル。著者や実績を装う語、架空の連載回数は入れない。
- `storySummary`：トップ一覧用の短い具体説明。タイトルの繰り返しではなく、本文で見る物や違いを書く。本文の結論・条件を越える約束をしない。
- `coverPhoto`：画像ID。captionは食材・工程の有用な説明がある場合のみ任意で付ける。免責の言い換えには使わない。ガイドは`meal`、用途比較は`bread`、アルファ米は`cooked-rice`を使う。通常の食品写真を掲載商品や実食の証拠として見せない。

題材を替える場合はラベル・説明・写真・リンク先を差し替える。非常食の数量計算、商品仕様、安全条件は共通テンプレートの文章へ埋め込まず、題材固有のデータ・本文として管理する。

### 避ける書き方

- 「わかりやすく整理しました」「信頼できる情報をお届けします」など、編集者の姿勢の宣伝。
- 「図で整理」「判断材料」「次の行動」だけの見出し。実際に見る物や操作の名前にする。
- 根拠のない「人気」「ベスト」「買ってよかった」「食べてみました」、架空の著者・監修者・取材・購入体験。「私たち」を添えて体験談に見せること。
- 「心がほどける備え」など内容から離れた美文、危機感を煽る表現、未測定の効果。
- すべてをカードに囲う、英語の小見出しと連番を飾る、同じ結論をタイトル・説明・カード・本文で繰り返す。

## 非常食固有の安全・機能契約

原文、`docs/sources/ledger.json`と一次情報の抜粋、`data/quantities.json`を正本として使う。公的目安と商品仕様の確認日を維持し、改稿した日を情報の再確認日に見せない。以下は文体や他の題材へ移すための都合で弱めない。

- 飲料水、注水用の水、生活用水を混同しない。水温・待ち時間・対象商品・注水量を一組で示す。
- 延べ食事回数、主食の袋数、熱量の合計を、食事全体や栄養の充足と同一視しない。主菜・副菜、食事制限、かむ・飲み込む配慮を残す。
- 原材料・アレルギー表示、通常品とアレルギー対応品の区別、現物表示の優先を残す。
- 保存表示と配送時の残存賞味期限を区別し、開封・調理手順、復元後、賞味期限切れの注意を保持する。
- 数値表、数量図、shortcode、明示アンカー、内部・外部リンクを保持する。出典番号は本文から除き、`evidenceKey` → `data/article-evidence.json`の命題・表行 → `docs/sources/ledger.json` → retrieval/excerptsで追跡する。読者には末尾の「参考にした情報」を13px/1.65で示す。図を軽く見せるために条件を隠さない。
- 在庫計算とメモ保存、買い足し不要の判定、通販検索リンクの正確な行動表示、個人データを外部へ送信しない条件を維持する。
- 改稿前後に`python3 docs/sources/verify.py`を実行する。これだけで意味や機能が保証されたとはせず、命題・警告・リンク・shortcodeの差分と、表示・操作を別に監査する。内部の原文snapshotや監査ログは公開repoへ入れない。

## 読者に残したいもの

このサイトの設計仮説は「家族が食に困らない生活を守りたい」→「家族が食べられる備蓄を必要分そろえたい」という目的と手段のつながりです。現状の障壁は「何をどれだけ買うか決められない」と仮定しています。顧客調査で確認した結果ではありません。

| ページ | 訪問時の未解決 | その場で進めること |
|---|---|---|
| トップ | どこから備えるか分からない | 家庭備蓄のガイドを主役に、写真と具体的な記事名から選ぶ。水の在庫が分かる人は下段で不足を計算する |
| ガイド | 家族分の必要量・食事の組合せが分からない | 不足量と食品在庫のメモを保存する |
| 用途比較 | 水・熱源・待ち時間と食品が結びつかない | 条件に合う候補を選び、原材料・配送条件を確認する |
| アルファ米 | 味・原材料・調理条件の違いで迷う | 候補を選び、注水量と待ち時間を備えに加える |

ニーズの上下は目的と手段の関係で、悩みの強さや購入の近さの順位ではありません。『水が不要』『長期保存』という仕様があることだけで、顧客がそれを欲しているとは認定しません。購入しない合理的な選択も残します。

## 視覚情報の標準

- 判断を助ける実写写真を主役にする。各写真の役割、利用条件、作者、出典、加工を `image-licenses.json` で管理する。
- 一般の食品写真を、紹介商品・実食・備蓄完了の証拠として使わない。現物を装うタイトル・alt・商品説明直下の配置を避ける。写真の帰属はフッターから一度で到達する「写真クレジット」に集約する。
- 定量的な主張は図を併設する。本文に数字を並べるだけで説明したことにしない。
- 図の単位、同じ尺度、基準量、温度条件、出典、数値と条件の対応を保つ。正確なDOMテキストと詳細表を残す。
- 日付・出典番号などのメタデータは図解対象外。本文で同じ数字を繰り返す場合も、対応する図と矛盾させない。
- 画像を入れるためだけにページを伸ばさない。詳細表・長い根拠は折り畳み、図・短い読み取り・次の行動を先に置く。

## 数値と図の対応

数値の共通正本は `data/quantities.json`、一次情報は `docs/sources/ledger.json` と抜粋です。

| 図ID | 説明する数量 | 必須の条件 |
|---|---|---|
| water | 人数と備蓄日数別の水量 | 飲料水の目安、調理・生活用水を別途検討 |
| meals | 人数込みの延べ食事回数 | 袋数や必要栄養量ではない |
| energy | 白飯の袋数と熱量合計 | 主食のみ。1日必要量の充足判定ではない |
| food-energy | 食品ごとの1袋・1個・1本の熱量と量 | 役割・分量が異なる。優劣ランキングではない |
| food-storage | 公式の保存表示・箱の入数 | 到着後の残存賞味期間を保証しない |
| rice-nutrition | 比較する米の熱量・たんぱく質・食塩 | 乾燥状態の1袋100g、成分別の尺度 |
| rice-weight | 乾燥重量・注水量・出来上がり重量 | 水の体積と食品の重量を混同しない |
| rice-prep | 注水量・水温・待ち時間 | 対象商品限定。水温15℃という条件を省かない |
| rice-water | 複数袋に必要な注水量 | この水だけで飲料・生活用水を賄えるわけではない |

## 公開前の判断

事実確認と技術テストに加え、別担当が次をレビューします。

1. 誰の望む状態と、現在の障壁を結びつけたか。
2. 写真・図だけでも、選択に必要な違いが分かるか。
3. 計算・確認・保存などの次行動を実際に完了できるか。
4. 買わない選択、安全条件、画像の利用条件を維持したか。
5. 見た目の改善や機能の動作を、未測定の売上・検索順位・顧客行動の改善と混同していないか。

Googleの公式説明は、制作手段よりコンテンツの品質・有用性を重視しています。『AIを使ったから一律に減点される』『画像を増やせば順位が上がる』を改修の根拠にしません。
参照：https://developers.google.com/search/blog/2023/02/google-search-and-ai-content

人数・在庫・食品メモを外部送信する計測は追加しません。操作検証と実利用者の行動変化は別の結果として扱います。

## 承認済み方向の固定と、監査と読者UXの分離

運営者は現在の北欧暮らし型、とくに豊富なアイコンを承認済み。写真の生活場面性など過去レビューの指摘を理由に、再び別デザインへ作り直さない。現在の写真3カット・構図・ヘッダー・文字組・余白を運用基準にする。

- 読者は記事を読むために来る。内部の確認作業を、繰り返す免責・英語のSources・番号・権利detailsとして押し付けない。
- 著者、原写真URL、licenseURL、帰属文、加工記録は原本`docs/image-licenses.json`を変更せず`/photo-credits/`へ出す。CC BY 2.0のwater-bottles/rice-grainsも含む。CC0の主写真も同じ一覧から確認可能にする。
- 商品仕様・数量表・安全条件の検査は省略しない。出典の表示場所を変えても内部の命題マッピングを維持する。行・カードの数値変更時は根拠とmappingを同時レビューし、テストを通すためだけに正本を変更しない。
- 運営説明はTIGRIT・目的・公的/メーカー情報の参照に絞る。広告未稼働の予定や非報酬の反復を読者へ表示しない。広告を有効化する時は、適切な広告表示、リンク属性、プライバシー説明を同時に更新してから公開する。
- 計算とメモは端末内。Cloudflare配信/解析の説明を残す。今回の変更には本番限定GA4タグと短いプライバシー説明を含む。UIの受入と解析の本番検証は別ゲートとし、配信後にGoogleへの通信・受信とGSC所有権を確認する。設定・検証・停止手順は `docs/analytics.md` を参照する。
- `npm test`を対象Hugo両版で実行し、PC/SPの初回画面・参考・クレジット・privacyを比較する。`npm run style-guide`で実部品のローカル見本を生成できる。見本は`tests/fixtures`から一時sourceにだけ配置し、公開content・一覧・sitemapへ出さない。
